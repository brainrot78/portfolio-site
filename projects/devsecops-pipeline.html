Case study · Sep 2025 – Dec 2025

Shift-Left
DevSecOps Pipeline

A Jenkins CI/CD pipeline for Spring Boot applications in which every stage runs a security check: leaked secrets, insecure code, vulnerable dependencies, risky container images and live web flaws. All findings end up in one place, DefectDojo.

01 / Why shift left

Find it at commit,
not in production.

A vulnerability costs the least to fix when the developer who wrote it is still looking at the code. Shift-left means moving security checks as early in the pipeline as possible, so problems are caught automatically on every commit instead of during a pentest weeks later.

I wanted a pipeline that covers the whole attack surface of a modern app: the source code, the secrets around it, the open-source libraries it depends on, the container it ships in and the running application. Each stage also needed to feed one dashboard, so nothing gets lost across five separate reports.

02 / The pipeline

Stage by stage

  1. 01CheckoutJenkins pulls the Spring Boot repo on every push
  2. 02 · SecretsGitleaksLeaked keys and tokens in code and git history
  3. 03 · SASTSonarQubeStatic analysis plus a quality gate
  4. 04 · SCAOWASP Dependency-CheckKnown CVEs in third-party libraries
  5. 05Build & imageMaven build, then the Docker image
  6. 06 · ContainerTrivyOS packages, libraries and misconfigurations in the image
  7. 07 · DASTNiktoScans the running app for web server flaws
  8. 08 · ReportDefectDojoImports results, removes duplicates, tracks fixes

03 / What each check catches

Five lenses on one app

Secret leak detection

Gitleaks

Scans the codebase and the full commit history for API keys, passwords, tokens and private keys. A secret that has been committed is already exposed, so this check runs first.

SAST

SonarQube

Analyses the Java source for vulnerabilities, security hotspots and code smells. A quality gate decides whether the build is good enough to continue.

SCA

OWASP Dependency-Check

Matches every Maven dependency against known CVEs. Most of an application's code comes from libraries, and this is where many real-world breaches start.

Container scanning

Trivy

Scans the built Docker image for vulnerable OS packages and libraries, and for misconfigurations, before the image is deployed anywhere.

DAST

Nikto

Tests the application while it is running: server misconfigurations, dangerous files, outdated components. These are problems you only see once the app is live.

Vulnerability management

DefectDojo

Every scanner's report is imported into one product view. Duplicates are merged, findings are triaged, and each one is tracked from open to verified fix.

04 / Takeaways

What I learned

Noise kills adoption. Five scanners produce a lot of overlapping results. Without deduplication in DefectDojo, developers would stop reading the reports within a week.

Order matters. Cheap, fast checks (secrets, SAST) run first and fail fast. Slower checks (container scanning, DAST) run only on builds that pass them.

Security should feel like testing. When security checks sit in the same pipeline as unit tests, they become part of "done" instead of a separate gate.
